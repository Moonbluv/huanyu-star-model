## 二、模块分工

```
core     HY.util · HY.world · HY.store（状态＋事件＋存储）· HY.calc（表与搜索）· HY.model（当前值与缓存）
gfx      HY.gfx：唯一渲染器与画布
overview HY.ov：总览三维（镜像双螺旋、塔影、分域、地点、标签、镜头）
fp       HY.fp：第一人称（uniforms 契约、噪声、地面镜像、天体、相机、设定映射、pass 图、实例、控制）＋ src/glsl/
charts   HY.charts：天空、一日、一年、日月高度、子午线、本月月相
ui       HY.ui：布局、时间栏、地点卡、读数、历法卡、参数、说明、第一人称 HUD、快捷键
app      HY.app：启动、帧循环、视图切换、测试接口
build    build.py：按 src/manifest.json 内联成单文件并做检查
```

数据只朝一个方向流：界面写 `HY.store` → 事件 → 各模块读 `HY.model` 自己画。

## 四、并行方案

M1 由一人（统筹）先做完，因为它定下全部接口；之后最多七路并行：

| 路 | 模块 | 依赖 | 可以先用桩开工吗 |
|---|---|---|---|
| A 核心计算 | core/world、calc、model ＋ 对应测试 | M1 的 store | 是 |
| B 总览三维 | gfx、overview/*、glsl/ov_* | M1；用 `HY.astro` 直接取数 | 是 |
| C 图表 | charts/* | A 的 `calc` 函数签名（03 第四节第 2 条，按签名先写返回假数据的桩） | 是 |
| D 界面 | ui/*、style.css、app 的启动与帧循环 | M1；A 的 `now` 字段（03 第四节第 3 条） | 是 |
| E 第一人称·管线 | fp/passes、fp/fp、fp/settings；大气、塔、日月、合成、后期着色器 | M1 的 uniforms 声明表与 DEFS | 是 |
| F 第一人称·地面 | fp/noise、fp/ground、地形着色器、地平线角图、fp/instances | 同上 | 是 |
| G 第一人称·天体与相机 | fp/celestial、fp/camera、fp/controls；HY.app 取数接口 | 同上 | 是 |

云（M5）在 E、F 交付后由 E 或 F 接手；它只往 DEFS 里加 pass、往 uniforms 表里加名字。

**接口怎么对齐**：

1. **只认三张契约表**，都在代码里、都有测试守着：`HY.store.SCHEMA`（状态路径、默认、范围）、`HY.fp.UNIFORMS`／`PRIVATE`（全部 uniform 的名、类型、写入方）、`HY.fp.passes.DEFS`（每个 pass 拼哪些 chunk、写哪个目标）。要改契约，改表并让 `store_check`、`glsl_check`、`params_check` 继续通过；不在表里的名字一律不许用。
2. **函数签名与返回形状以 03 为准**（`HY.calc`、`HY.model.now`、视图接口、图表接口、`HY.app` 取数接口）。实现前先写桩，按签名返回固定假数据，让下游可以同时开工。
3. **写入方唯一**：每个 uniform、每条状态只有一个写入模块（03 第三节第 3 条、第七节第 2 条）；视图、图表不改别人的状态。
4. **一个公式只有一份实现**：日月几何只在 `astro.js`；`towerVis`／`eclipseVis` 的 GLSL 只在 `common.glsl`，总览的副本由测试逐字比对；地面函数 GLSL 与 JS 镜像同式，由 `noise_mirror`、`terrace_geom` 对拍。
5. **每晚合一次**：各路提交前跑 `py build.py --test`；构建失败或任何 node 测试失败不合入。
